## Сервис назначения ревьюеров для Pull Request’ов

Этот проект — небольшой микросервис, который автоматически назначает ревьюеров на Pull Request’ы внутри команды.
Сервис поднимается через `docker-compose` и общается с внешним миром только по HTTP (OpenAPI спецификация лежит в репозитории).

---

## Описание

Сервис реализует базовую логику работы с командами, пользователями и PR:

* При создании PR автоматически выбираются до двух активных ревьюеров из команды автора.
* Можно переназначить одного ревьювера на случайного активного участника **из его команды**.
* После того как PR смержен, менять ревьюверов запрещено.
* Можно получить список PR по пользователю.
* Есть базовые CRUD-операции над командами и пользователями.

Большая часть логики описана в OpenAPI (`openapi.yaml`), от которой я отталкивался при проектировании схемы БД и бизнес-слоя.

## Как запустить

### 1. Склонировать репозиторий

```bash
git clone <url>
cd <папка проекта>
```

### 2. Собрать и поднять сервисы

```bash
docker-compose up --build
```

Это поднимет:

* контейнер `db` (Postgres),
* контейнер `migrate`, который применит миграции к БД,
* контейнер `app` — само приложение на Go.

После успешного старта приложение доступно по адресу:

```
http://localhost:8080
```

### 3. Проверить, что приложение работает

```bash
curl http://localhost:8080/health
```

Должно вернуть `ok`.

## Миграции

Миграции выполняются автоматически при запуске `docker-compose up`.
Используется официальный CLI `migrate/migrate`.
Все SQL-файлы лежат в папке `migrations/`.

Основные сущности:

* `teams`
* `users`
* `pull_requests`
* `pr_reviewers`

Добавлены триггеры, которые:

* запрещают менять ревьюверов после `MERGED`,
* ограничивают список ревьюверов до двух человек,
* автоматически проставляют `merged_at` при переводе PR в `MERGED`.

## Решения и допущения

По условию не всё было однозначно, поэтому несколько моментов я сформулировал так:

1. **Пользователь принадлежит только одной команде.**
   В OpenAPI возвращается `team_name` у User, значит в БД это FK.

2. **Переназначение ревьювера работает только в пределах команды ревьювера.**
   Если активных кандидатов нет — возвращаю ошибку с нужным кодом.

3. **Конкурентные изменения PR.**
   В критичных местах использую транзакции и `FOR UPDATE`, чтобы избежать гонок.

4. **MERGE — идемпотентная операция.**
   Если PR уже в статусе `MERGED`, метод просто отдаёт его текущее состояние.

5. **Не стал подключать лишние фреймворки.**
   На небольшом сервисе обычный `net/http` и sqlx дают большую прозрачность.

## Как пользоваться API

Все эндпоинты описаны в `openapi.yaml`.
Пример стандартного запроса можно выполнить через curl:

```bash
curl -X POST http://localhost:8080/teams \
    -H 'Content-Type: application/json' \
    -d '{"team_name": "backend"}'
```
